# 09 · 节点自组网（草案 1）

> 2026-11-22 起草。本篇取代 [03](03-节点联邦.md) 里「管理员手工互连、只转一跳」的做法，03 留作历史参考。

## 目标

各地玩家用**自己的服务器**（云主机、有公网 IP）起一台节点，不用找任何人审批，几分钟后：
- 全网的客户端都能发现它；
- 附近的玩家会被分流到它上面；
- 它上面的公开房间，全网都看得到；
- 它停了，网络自动把它摘掉。

网络里的节点越多，每个地区可选的节点就越多，承载能力也随之增长。这就是「自扩展」。

## 不做的事

- **不做家宽穿透。** 节点要有公网可达的地址（IPv4 或 IPv6，加一个端口）。家宽玩家当客户端用，不当节点。
- **不做跨节点战绩互认。** 对局由主机裁决，主机能改结果，各节点的战绩和天梯各算各的（同 03）。
- **不做去中心化共识。** 名录是少数几台、彼此信任的服务器，用简单的同步就够，不上区块链、DHT 这类东西。
- **不替运营者解决合规问题。** 见 [合规](#合规)。

## 角色

| 角色 | 是什么 | 谁来运营 |
|---|---|---|
| 节点 | 现有的 `tablenet-node`：房间、排队、对局通道、适配器 | 任何人 |
| 名录 | 收节点名片、做探测、回答「附近有哪些节点」 | **只由项目方运营**（11-22 定），国内、香港各至少一台 |
| 探测点 | 从某个地区去连节点，量一量连不连得上、多快 | 项目方；名录自带，另可单独部署 `tablenet-probe` |
| 协调节点 | 第二期：某个地区、某种赛制的排队由它撮合 | **只由项目方运营**，不轮值 |

名录和探测点可以和节点跑在同一个程序里（`tablenet-node` 开一个开关），也可以单独部署。

## 信任锚

- 项目有一把**根密钥**（Ed25519），由项目方（官方）持有、离线保存，不放在任何联网的服务器上。
- 另生成一把**备用根密钥**，同样离线保存。两把公钥都写进代码；清单用哪一把签都认。主根密钥丢失或泄露时，改用备用钥签清单，并在下一个版本里换上新的备用公钥。
- 根密钥签发一份**名录清单** `directories.json`：每台名录的编号（公钥）、地址、所在地区、有效期。
- 节点和客户端代码里写死根公钥，以及两三个拉取清单的地址（国内、香港各一）。拉到清单后先验签，再用。
- 名录清单是唯一需要根密钥签名的东西；节点名片由节点自己签，名录只能转发或拒收，**改不了**。

换名录服务器只需要重签一份清单，不用发新版客户端。这条和 0.3「中继地址写死、换服务器只改解析」是同一个思路，但多了一层签名，防止被劫持到假名录。

## 节点名片

### 格式

名片是一段 JSON **原文**，连同签名一起传。签的就是这段原文的字节，不做 JSON 规范化（和战绩 `reportText` 同一个做法，见 01）。

```json
{
  "card": "{\"v\":1,\"nodeId\":\"ed25519:…\",\"seq\":42,\"issuedAt\":\"2026-11-22T08:00:00Z\",\"expiresAt\":\"2026-11-22T08:30:00Z\", …}",
  "sig": "b64:…"
}
```

签名内容是 `"tablenet/1 node-card" || card`。`card` 解开后的字段：

| 字段 | 说明 |
|---|---|
| `v` | 名片格式版本，现在是 1 |
| `nodeId` | 节点编号（公钥），必须和签名的密钥一致 |
| `seq` | 单调递增。名录只收比已知更大的 `seq`，旧名片重放无效 |
| `issuedAt`／`expiresAt` | 有效期，最长 30 分钟。节点每 10 分钟重签一次 |
| `name` | 展示名，1–40 字 |
| `region` | 节点自报的地区，取值见 [地区](#地区) |
| `endpoints` | 对外地址列表，每项 `{url, tlsSha256?}`，例如 `wss://203.0.113.7:8443/tablenet/1`。至少一项 |
| `protocols` | 支持的协议版本，例如 `["tablenet/1"]` |
| `features` | 同 `node.hello.features` |
| `venues` | 挂了哪些适配器（外部平台编号），以及每个平台支不支持桥接 |
| `capacity` | 运营者声明的上限：`{players, rooms, relayMbps}` |
| `load` | 当前负载：`{players, rooms, channels}`，节点每次续期时更新 |
| `status` | `open`（正常接客）、`draining`（不接新局，等现有对局打完）、`private`（只登记不推荐，凭名字或编号能找到） |
| `operator` | 可选：运营者自愿公开的联系方式或网址 |
| `software` | `{name, version}` |

名片上限 4 KiB。

### 登记

节点用 WebSocket 连名录（地址来自名录清单），握手方式同 01（`role: "node"`），然后：

```json
{ "type": "dir.register", "id": "r1", "body": { "card": "…", "sig": "b64:…" } }
```

名录回 `dir.registered {seq, listed, reasons}`：
- `listed: false` 时 `reasons` 写原因，例如 `probe_pending`、`unreachable_from:cn-north`、`rate_limited`、`protocol_too_old`、`delisted`。
- 新节点第一次登记时，名录先**探测**（见下），通过之后才对客户端公开。

节点在名片快到期前续期（再发一次 `dir.register`，`seq` 加一）。连着的那条 WebSocket 断了也不要紧，下次续期时重连；名录只看名片有没有过期。

节点要下线时，发一张 `status: "draining"` 的名片，等对局打完后停机。名片过期后，节点自动从名录消失。

### 一台节点登记到哪几台名录

节点同时登记到**名录清单里它所在地区的名录，再加一台其他地区的**（例如国内节点登记国内一台、香港一台）。名录之间还会互相同步（见下），多登一台是为了某台名录挂了也不影响。

## 名录之间的同步

- 每台名录记着全部已知名片，每收下一张新名片，就给它一个本地递增的**变更序号**。
- 名录之间互相拉取：`GET /dir/v1/changes?since=<序号>`，回这个序号之后的所有名片（原文＋签名），外加探测结果。每 5 秒拉一次。
- 收到别的名录转来的名片，照样验签、比 `seq`，只收更新的。名录改不了名片内容，所以同步时不需要信任对方名录。
- 探测结果是名录自己的观测，由名录用自己的密钥签名，附在名片旁边一起转发。别的名录可以采信，也可以只用自己的探测结果。

规模估计：一万台节点、每台 2 KiB 名片、每 10 分钟续一次，全网每秒约 34 KB 的同步量，一台小服务器就扛得住。

## 探测

**为什么要探测：** 国内节点从海外连可能时好时坏，反过来也一样。节点自报的「能连上」不可信，要从各个地区实际连一次。

- 探测按三个**探测区**做：`cn`（中国大陆）、`hk`（香港）、`intl`（其他海外）。第一版每个探测区一个点就够：
  - 国内名录、香港名录各自兼任 `cn`、`hk` 的探测点（名录进程里自带探测，不另起机器）；
  - `intl` 用一台便宜的海外云主机跑独立的 `tablenet-probe`（只会探测、不存东西，连名录上报结果）。
  以后要更细（国内分南北、分运营商），加探测点即可，协议不变。
- 探测内容：
  1. 连节点名片上的每个地址，做 TLS 握手，校验证书指纹（如果名片里写了）；
  2. 走一遍 Tablenet 握手，**校验节点身份证明**（见 [节点证明身份](#节点证明身份)），确认对面就是这把密钥；
  3. 记下往返时间。
- 新节点：登记后立即探测，通过才公开。
- 已收录的节点：每 5 分钟抽探一次。连续 3 次从某个地区连不上，就对那个地区的客户端隐藏它（其他地区照常）。
- 探测结果：`{nodeId, probeRegion, ok, rttMs, at}`，由名录签名。

## 节点证明身份

现在的握手里，节点发来了自己的编号，客户端却没有验证它真的持有这把密钥。自组网之后，冒充别人的节点就成了真风险，所以要补上：

- 客户端的 `hello` 里加 `nodeChallenge: "b64:<随机 24 字节>"`；
- 节点在 `welcome` 里回 `nodeProof`，签名内容是 `"tablenet/1 node-proof" || nodeChallenge || playerId || nodeId`；
- 客户端拿名录给的名片公钥验签，不对就断开。

### 不需要域名和正规证书

很多运营者只有「IP:端口」，没有域名，也拿不到受信任的 TLS 证书（国内服务器用域名对外提供网站服务还要先备案）。所以：

- 节点可以用**自签证书**，把证书的 SHA-256 指纹写进名片的 `endpoints[].tlsSha256`；
- 客户端连这类地址时，**按名片里的指纹校验证书**，不走系统的证书链；
- 名片由节点密钥签名，节点身份又由上面的证明核实，所以就算没有正规证书，中间人也冒充不了。

`tablenet-node init` 默认生成自签证书，并把指纹自动写进名片。有域名和正规证书的运营者照常配置即可。

## 地区

第一版用一张粗粒度的固定表：

`cn-north`、`cn-east`、`cn-south`、`cn-west`、`hk`、`tw`、`jp`、`kr`、`sea`、`eu`、`na`、`oceania`、`other`。

- **暂不按运营商细分**（11-22 定），以后再说。
- 节点自报地区，名录用探测延迟粗查：比如自报 `cn-east`，可 `cn` 探测点测出 200 ms，就标成「地区存疑」，排序时降权。
- 地区和探测区的对应：`cn-*` → `cn`，`hk` → `hk`，其余 → `intl`。客户端在哪个探测区，就只看在那个探测区连得上的节点。
- 不用第三方的 IP 地理库，免得依赖外部数据、也省得为此上传玩家地址。

## 客户端怎么挑节点

1. 启动时先拉名录清单并验签，再从一台名录取节点列表：

   `GET /dir/v1/nodes?region=cn-east&protocol=tablenet/1&venue=hexproof&limit=20`

   `region` 由客户端自报（玩家在设置里选，或者按系统时区猜一个默认值），名录不记录客户端 IP。
2. 名录按下面的顺序排好返回：**信任档 → 在这个地区连得上 → 负载低 → 延迟低**。每项附名片原文、签名和探测结果。
3. 客户端自己再测一遍前几台的延迟，挑最好的连上。玩家也可以手动指定节点，或者收藏常用的节点。

**网络就是这样自动分流的**：名录按负载排序，新来的节点自然会分到人。

## 信任分级与防滥用

| 档 | 条件 | 客户端默认 |
|---|---|---|
| 认证 | 有项目根密钥签的「认证记录」（`{nodeId, issuedAt, expiresAt, note}`） | 优先推荐 |
| 稳定 | 登记满 7 天、近 7 天在线率 ≥ 90%、探测正常、没被下架 | 正常推荐 |
| 新节点 | 其他 | 不进推荐列表；凭名字、编号搜得到，可以手动加入 |

**防滥用：**
- 登记限流：同一 IPv4 /24（IPv6 /48）每小时最多 5 次新登记，同一地址最多挂 3 台节点。
- 名片大小、字段长度设上限；名称里不许冒用「官方」「认证」之类的字样（名录按词表拦）。
- **暂不做玩家举报**（11-22 定）。以后要做时，用玩家密钥签名的举报，按「多少个不同的玩家在举报」累计。
- **下架：** 名录维护一张下架表（整台下架、或只在某些地区隐藏），由项目方用命令行人工操作，同步到其他名录。下架只影响「被推荐、被发现」，不影响玩家手动直连那台节点。
- **冒充做不到：** 身份就是公钥，名片要签名，握手要证明身份。

## 版本协同

- 名录只把客户端讲得通的节点推给它（比对 `protocols`）。
- 节点的 `software.version` 落后太多时，名录在 `dir.registered` 里带 `upgrade` 提醒（建议版本＋说明链接），运营者用 `admin status` 能看到。
- 名片格式自身也有 `v`：名录同时认当前和上一个版本，给运营者留一个大版本的升级窗口。

## 节点自身要补的（并网的前提）

自组网之后，玩家会被分流到别人运营的节点上，节点的稳定性就关系到整个网络的口碑。第一期必须一起补上：

- **状态落盘：** 房间、排队、续接表写进本地数据库（初稿倾向 SQLite），重启后恢复。玩家在 120 秒内重连，就能接回原来的房间和排队位置。
- **优雅停机：** `tablenet-node drain` 先把名片改成 `draining`，不再接新局，等现有对局打完或超时后再退出。
- **`/metrics`：** 在线人数、房间、通道、转发流量、握手失败、限流次数。
- **主机接管**（规范 01 里的 `host-takeover`）：第三期做，但要先把接口留好。

## 第二期：全网房间与跨节点匹配（先定方向，细节第二期再写）

**全网房间索引**
- 节点把公开房间的摘要（不含任何玩家隐私）每 10 秒推给登记的名录，名录之间照名片的方式同步。
- 客户端向名录查全网房间（可以按地区、赛制、平台过滤），入座时直接连房间所在的节点。房号本身带着节点编号，冒充不了。

**跨节点匹配**
- 排队按「地区×赛制×局制」分池。每个池由一台**协调节点**撮合，名录清单里写明哪个池归谁。
- 玩家照常在自己连着的节点上排队，节点把排队单转给对应的协调节点；配上之后，协调节点挑一台离双方都近、负载低的节点开房，把房号发回给双方。
- 跨境对局（国内对海外）优先落在 `hk` 的节点上。
- **协调节点只由项目方运营，不轮值**（11-22 定）。第一版一台协调节点管全部池子（排队只是转发和配对，量很小），名录清单里写它的地址；量大了再按地区拆成几台。协调节点挂了，各节点退回「只在本节点内排队」，不影响已开的对局。

## 合规

在中国大陆面向公众运营网络游戏服务，可能涉及 ICP 备案和网络游戏运营方面的资质。

- Tablenet 是开源软件，协议开放。**每台节点由谁运营，谁负责**，项目方不为第三方节点担保。
- `tablenet-node init` 生成配置时要提示这一点，并且默认把名片设为 `status: "private"`（只登记、不进推荐），由运营者确认后再改成 `open`。
- 名录运营者要能按法律要求或主管部门通知下架节点（见上面的处罚表）。
- 名录不记录玩家的 IP 地址，也不存任何对局内容。

## 分期

| 期 | 内容 | 做完以后 |
|---|---|---|
| 第一期 | 名录清单与根密钥、节点名片、登记与续期、名录同步、多地探测、节点证明身份、证书指纹、客户端挑节点、节点状态落盘、优雅停机、`/metrics` | 任何人起一台节点就能被全网发现、被就近分流 |
| 第二期 | 全网房间索引、跨节点匹配与协调节点、信任分级、下架表同步 | 网络对玩家来说像一个整体 |
| 第三期 | 主机接管、端到端加密、iroh 直连（省节点带宽） | 掉线不丢局、对局内容对节点不可见 |

## 第一期实现（tablenet 0.2，2026-11-22）

和上文不一样、或者上文没写细的地方：

| 项 | 实现 |
|---|---|
| 登记方式 | 用 HTTP 而不是 WebSocket：`POST /dir/v1/register {card}`。名片自带签名，不需要长连接和握手 |
| 名片外形 | `{text, sig}`，签名内容是 `"tablenet/1 node-card" || text`。名录清单另带 `signer`，探测结果、下架、认证用 `{text, sig, signer}` |
| 名录 HTTP 接口 | `/dir/v1/register`、`/dir/v1/nodes`、`/dir/v1/changes?since=`、`/dir/v1/observations`、`/dir/v1/directories.json`、`/healthz`；管理接口只听本机：`/status`、`/nodes`、`/delist`、`/endorse` |
| 名片续期 | 每 10 分钟；名录回「探测中」时 30 秒后再登记一次；失败 1 分钟后重试 |
| 节点状态落盘 | 用 JSON 快照（`data_dir/state.json`，每 15 秒和退出时写），不用 SQLite：量很小，也免了 cgo |
| 排空 | `tablenet-node admin drain`：不接新开房、新排队、还没开打的房不再收人；名片立刻改成 `draining`。已开打的局照常（掉线回来、观战） |
| 不需要域名 | `tablenet-node init --region … --public-host …` 生成自签证书、写好并入自组网的配置，名片默认 `private` 并打印合规提醒 |
| 根密钥工具 | `tablenet-dir root keygen／sign-list／endorse`，离线用；签名时只读密钥、不会误生成 |
| 独立探测点 | `tablenet-probe --dir … --zone intl`，公钥写进名录清单的 `probes` |
| 客户端 | Go：`pkg/discovery`（取清单、查节点、按指纹配 TLS）＋ `client.DialNode`（验节点证明）。Rust SDK：`tablenet_proto::signed`（验名片、验清单、验节点证明）＋ `Client::connect_node`；**Rust 端的证书指纹校验还没做**（要给 tokio-tungstenite 配 rustls 连接器），独弈接入时补 |
| 根公钥和清单地址 | 代码里留了位置（`pkg/discovery` 的 `DefaultRoots`、`DefaultListURLs`，可构建时注入），**现在是空的**，等项目方生成根密钥、部署名录后填 |

测试：`internal/directory` 单测（seq 防重放、登记限流、探测者必须在清单里、连续 3 次失败隐藏、下架必须名录签、落盘往返、版本比较）；`internal/node` 端到端（两台名录＋自签证书节点：登记 → 两区探测 → 同步 → 按指纹连上并验身份 → 根密钥认证 → 排空 → 下架与撤销）；真进程冒烟（三个可执行文件、根密钥签清单、海外探测点）。

## 只有一台香港名录时（第一版的实际部署）

- **名录只管「发现」，不管对局。** 客户端从香港名录拿到节点列表后，直接连自己挑的那台节点，对局流量不经过香港。国内玩家连国内节点，延迟和香港无关。
- **名录挂了不影响已经在打的局**，也不影响「收藏过的节点」：客户端把最近拿到的节点列表和收藏的节点存在本地，名录连不上时照样能连这些节点。节点身份靠握手时的身份证明核实，不依赖名片是否过期。只有「发现新节点」会暂时用不了。
- **国内能不能连上一台节点，名录测不了**（香港测得到不代表国内测得到，反过来也一样）。所以客户端拿到列表后，自己测前几台的延迟，连不上的跳过。国内的云主机从国内连一般没问题，这一点代价不大。
- 节点登记只登记这一台（`targets()` 在清单里只有一台名录时就选它）。
- 以后要加名录或探测点，重签一份名录清单即可，节点和客户端都不用发新版。
