# 03 · 节点联邦（tablenet/1，草案 0）

联邦是**可选**特性（`federation`）。不开联邦的私服照样能用，只是它的玩家只看得到这一台节点上的房间。

## 目标与边界

**做：** 私服之间互相看得到公开房间；一台节点上的玩家能入座另一台节点上的房间。
**第一版不做：** 跨节点排队匹配、跨节点战绩和天梯、跨节点私信。原因见文末。

## 节点之间怎么连

- 节点管理员在配置里写对端：`peers = ["wss://node-b.example.org/tablenet/1"]`。**没有**自动发现，也不搞全网广播，只连管理员点名的对端。
- 连接时用 `role: "node"` 握手，签名的是节点密钥。双方都在对方的 `peers` 里，才算建立联邦。
- 对端管理员**可以**随时把某台节点拉黑（按 `nodeId`），拉黑后它发来的房间全部撤下。

## 互传房间

建立联邦后，节点把自己的**公开**房间推给对端：

```json
{ "type": "fed.room.upsert", "body": { "room": { "roomId": "node-a.example.org/K7Q2MD", "...": "..." }, "ttl": 120 } }
```

- 只推 `visibility: "public"` 的房间。
- 每条带 `ttl`（秒），对端到期没收到刷新就撤下。源节点**应当**每 60 秒刷新一次仍在的房间。
- **只转一跳。** 对端收到的联邦房间**不得**再推给它自己的对端。这样一来，看得到哪些房间完全取决于自己连了谁，不会被远端的节点灌满。
- 联邦房间在本地房间表里照常显示，`roomId` 的主机名部分告诉玩家这间房在哪台节点上。
- 外部平台的房间（适配器发布的）**默认不转**，因为交接链接要那台节点上的适配器来发，跨节点之后签不出来。节点管理员可以单独打开。

## 跨节点入座

玩家点了一间别的节点上的房间：

1. 客户端看 `roomId` 的主机名，直接连那台节点（`wss://<主机名>/tablenet/1`），照常握手；
2. 在那台节点上 `room.join`，后面的流程和本地入座一样。

节点之间**不**代转对局流量。理由：转一次多一跳延迟，而且两台节点之间的带宽是管理员自己掏钱的。
客户端同时连两台节点是正常情况，客户端实现**应当**支持。

## 身份怎么跨节点

玩家的 `playerId` 就是公钥，所以走到哪台节点都是同一个人，不需要两台节点之间同步账号。
每台节点自己决定收不收这个人：黑名单、限流、要不要先在网页上注册，都是各节点自己的事。

## 为什么第一版不做跨节点排队

- 排队要求两台节点对「谁先排、谁跟谁配」有一致的看法，等于要做分布式一致性，代价远大于收益。
- 私服的玩家量一般不大，跨节点排队真正需要的是「小服玩家想排到大服去」。直接让客户端同时连大服排队就能解决，不用节点出手。

## 为什么不做跨节点战绩

对局由主机裁决，主机能改结果。一台节点信任它自己的玩家，但没理由信任另一台节点转来的战绩。
各节点的战绩、分数各算各的；玩家想展示，就自己把签过名的 `result.confirm` 导出来给人看。

## 和别的联邦协议的关系

思路上接近 Matrix 和 ActivityPub（各管各的人，彼此转公开内容），但刻意做得小：只转房间表、只转一跳、不转对局。
将来真需要的话，可以在 `tablenet/2` 里再加多跳和跨节点排队。
