# 02 · 适配器协议（tablenet/1，草案 0）

适配器是替一个外部平台说话的独立进程。它以 `role: "adapter"` 连上节点，用的信封、握手、心跳和 [01](01-客户端协议.md) 完全相同。

**谁来写适配器：** 节点运营者自己写，或者外部平台的运营方写，都可以。Tablenet 项目自带三个：
- `adapters/example`：假平台，演示协议、跑一致性测试，MIT；
- `adapters/xmage`：接 XMage 服务器，MIT（XMage 本身是 MIT，依赖它的 `Mage.Common`），详见 [07](07-首批适配器.md#xmage)；
- `adapters/hexproof`：接 Hexproof hub，GPL-3.0（照它的 `protocol/v3` schema 实现），详见 [07](07-首批适配器.md#hexproof)。

每个适配器是单独的程序，目录里放自己的 `LICENSE`。节点本体**不得** import、链接或打包任何适配器的代码，只通过本篇的协议和它们说话，所以即使是 GPL 的适配器（Hexproof 那个）也不影响节点的 MIT。
闭源平台（例如 Endstep）没有公开协议，Tablenet 不逆向，只能等它的运营方自己按交接档接入。

**连别人的服务器要先问。** 适配器登录到别人运营的 XMage 服务器或 Hexproof hub，相当于在那里挂一个机器人账号，**必须**先取得那台服务器运营者的同意。连你自己部署的服务器则没有这个问题。

## 适配器身份

- 适配器有自己的一对 Ed25519 密钥，`hello` 时一样签名。
- 一个 `platformId` 在一台节点上同一时刻只能有一个适配器在线。节点第一次见到某个 `platformId` 时记下它的公钥（先到先得），之后换钥匙要节点管理员手动放行。
- 节点管理员可以在配置里把某个 `platformId` 钉死在某把公钥上，防止冒名。

## 握手

```json
{ "type": "hello", "id": "a1", "body": {
  "protocol": "tablenet/1",
  "role": "adapter",
  "playerId": "ed25519:...",
  "sig": "b64:...",
  "platform": {
    "platformId": "endstep",
    "name": "Endstep",
    "homepage": "https://endstep.cc",
    "joinKinds": ["handoff"],
    "formats": ["standard", "modern", "commander", "cube", "x-endstep-forgetful-fish"],
    "gameTypes": ["duel", "ffa"],
    "structures": ["bo1", "bo3"],
    "codecs": [],
    "accountLink": "optional",
    "terms": "https://endstep.cc/terms"
  },
  "client": { "name": "endstep-tablenet-adapter", "version": "1.0.0" }
} }
```

| 字段 | 说明 |
|---|---|
| `platformId` | 小写字母、数字、连字符，3–32 位。`native` 和 `x-` 开头的保留 |
| `joinKinds` | 这个适配器支持哪几档：`handoff`、`bridge` |
| `formats` / `gameTypes` / `structures` | 这个平台能开什么样的局。节点据此决定哪些排队池子能匹配到这个平台 |
| `codecs` | 桥接档才有：适配器能把对局转成哪些编码 |
| `accountLink` | `none`、`optional`、`required`：玩家在那个平台有没有账号要不要先和 Tablenet 身份绑定（见 [账号绑定](#账号绑定)） |
| `terms` | 那个平台的服务条款链接，客户端第一次交接到这个平台时**应当**给玩家看 |

节点回 `welcome`，之后它出现在玩家 `welcome.platforms` 里。

## 交接档

交接档是门槛最低的一档：适配器只管房间，不碰对局。玩家拿着链接去对方平台自己的客户端里打。

### 发布房间（可选）

对方平台上公开的房间，适配器可以发布到节点的房间表里，让 Tablenet 玩家看得见：

```json
{ "type": "venue.room.upsert", "body": {
  "localId": "88213",
  "title": "Vintage Cube 8 人",
  "format": "cube", "gameType": "draft-pod",
  "seats": { "total": 8, "taken": 5, "ai": 0 },
  "structure": "bo1", "hasPassword": false, "visibility": "public",
  "status": "waiting",
  "spectate": { "allowed": true, "seeHands": false }
} }
```

- 节点给它分配 `roomId`：`<节点主机名>/<platformId>-<localId>`，`venue` 填 `platformId`，`join.kind` 填 `handoff`。
- 状态变了再发一次 `venue.room.upsert`；房间没了发 `venue.room.remove {localId}`。
- 适配器断线 60 秒后，节点**必须**撤下它发布的全部房间。
- 适配器**不得**发布对方平台上不公开的房间，也**不得**发布对方玩家的账号名，除非对方玩家自己同意。房主名一律填 `host: null`，或者由那个平台给出一个公开的展示名。

### 有人要入座

玩家在 Tablenet 里点了这间房，节点问适配器：

```json
{ "type": "venue.seat.request", "id": "n31", "body": {
  "localId": "88213",
  "player": { "playerId": "ed25519:...", "displayName": "小明", "locale": "zh-CN", "linked": null },
  "as": "player",
  "password": null
} }
```

适配器回：

```json
{ "type": "venue.seat.granted", "re": "n31", "body": {
  "url": "https://endstep.cc/t/88213?k=...",
  "code": "88213",
  "expiresAt": "2026-11-22T08:05:00Z",
  "note": "在 Endstep 网页里打开，需要登录 Endstep 账号"
} }
```

或者回 `error`（`room_full`、`wrong_password`、`no_room` 等）。节点把结果原样包进 `room.joined` 发给玩家。

没有网页入座链接的平台（XMage、Hexproof 都是填服务器地址再进房），不给 `url`，改给 `connect`：

```json
{ "type": "venue.seat.granted", "re": "n31", "body": {
  "connect": { "client": "xmage", "server": "xmage.example.org:17171", "room": "Tablenet 90017", "password": "k3v9q" },
  "expiresAt": "2026-11-22T08:05:00Z",
  "note": "打开 XMage 客户端，连这台服务器，在主房间找这张桌子"
} }
```

`connect` 里的字段由各平台自己定，`client` 必填，客户端靠它决定怎么展示（复制按钮、说明图）。`url` 和 `connect` 至少给一个。

- `url` **必须**是 `https://`，并且主机名属于 `platform.homepage` 那个域。节点**必须**校验这一条，不符合就丢弃，防止适配器把玩家引到钓鱼页。
- `connect.server` 的主机名**必须**在节点配置里登记过（`[adapters.<平台>] servers = [...]`），理由同上。
- 链接里**可以**带一次性入座凭证，有效期**应当**不超过 10 分钟。
- 节点 10 秒内收不到回话，就给玩家回 `venue_unavailable`。

### 按请求开房

排队配对落到这个平台时，节点请适配器开一间房：

```json
{ "type": "venue.room.create", "id": "n40", "body": {
  "matchId": "m_19c",
  "format": "modern", "gameType": "duel", "structure": "bo3",
  "players": [
    { "playerId": "ed25519:...", "displayName": "小明", "linked": null },
    { "playerId": "ed25519:...", "displayName": "阿强", "linked": { "account": "aqiang" } }
  ],
  "visibility": "private",
  "spectate": { "allowed": false }
} }
```

适配器回 `venue.room.created`，每位玩家各一条入座链接：

```json
{ "type": "venue.room.created", "re": "n40", "body": {
  "localId": "90017",
  "seats": [
    { "playerId": "ed25519:...", "url": "https://endstep.cc/t/90017?k=aaa", "expiresAt": "..." },
    { "playerId": "ed25519:...", "url": "https://endstep.cc/t/90017?k=bbb", "expiresAt": "..." }
  ]
} }
```

开不了就回 `error`，节点把双方放回排队（不算他们拒绝）。

### 结果回报（可选）

那个平台上这局打完，适配器**可以**发 `venue.result {localId, matchId?, players:[{playerId, games}], reason}`。
节点把它当作「平台担保」的结果记下，不再要双方签 `result.confirm`。节点要不要信某个平台的担保，由节点管理员配置。

## 桥接档

桥接档里，玩家用讲 Tablenet 的客户端打牌，局面来自对方平台的服务器，适配器在中间翻译。

- 适配器声明 `joinKinds` 含 `bridge`，并在 `codecs` 里列出它能输出的编码。
- 入座流程同交接档：节点发的 `venue.seat.request` 里 `bridge: true` 表示这位玩家能解这间房的编码、希望桥接；适配器回 `venue.seat.bridged {}`，节点开一条对局通道（一头是玩家，一头是适配器），并给适配器发 `channel.opened {channel, roomId, localId, as, player}`，和原生房主机收到的一样。
- 玩家解不了编码时 `bridge` 为 false；平台也支持交接档的话，按交接档回链接或 `connect`，否则节点直接回玩家 `codec_mismatch`。
- 排队配到桥接平台时，`venue.room.create` 的 `players[].bridge` 标出谁能桥接；`venue.room.created.seats[]` 里给这位玩家写 `bridge: true`（不给链接），节点开通道、发 `match.bridged`。
- 通道里的负载格式由 `codec` 决定。tablenet/1 **不规定**任何对局编码的内容，只规定编码名的登记方式（见下）。
- 客户端只有声明了同一个 `codec` 才能进桥接房，否则节点回 `codec_mismatch`。

### 对局编码登记

编码名写成 `<作者>.<名字>`，例如：
- `arcane.v0`：独弈现有的对局协议，规范是独弈仓库里的 `packages/protocol-schema/protocol-v0.schema.json`，是否随 Tablenet 公开见 [待定问题](05-待定问题.md)；
- `hexproof.v2`：Hexproof 的协议（由它的作者决定是否登记）。

本仓库根目录放一张 `codecs.md`，记录每个编码的名字、维护者和规范链接。登记只是记名字，Tablenet 不审内容。

实际情况是，一个客户端要能打某个平台的桥接局，得自己实现那个平台的编码。所以桥接档能不能成，取决于有没有客户端愿意实现；第一版的重点应该放在交接档。

## 账号绑定

有的平台要求玩家先登录自己的账号，才能入座。`accountLink` 为 `optional` 或 `required` 时：

1. 玩家在客户端里点「绑定 Endstep 账号」，客户端发 `link.begin {platformId}`；
2. 节点问适配器 `venue.link.begin {playerId}`，适配器回一个那个平台上的授权链接（OAuth 或者它自己的确认页）；
3. 玩家在浏览器里登录、同意；
4. 适配器发 `venue.link.done {playerId, account, displayName?}`，节点记下这条绑定，之后的 `player.linked` 里带上它。

- 节点**只**存 `account` 这个公开标识，**不得**经手对方平台的密码、令牌或 Cookie。
- 玩家可以随时发 `link.remove {platformId}` 解绑。
- 绑定只在这台节点上有效，联邦时不外传（见 [03](03-节点联邦.md)）。

## 一致性测试

Tablenet 仓库提供 `tablenet-conformance` 工具：起一台测试节点，按脚本扮演玩家，检查适配器的每一条回话。
适配器作者跑通它，就可以在本仓库根目录的 `adapters.md` 里登记。登记不代表 Tablenet 为这个平台担保。

## 错误码（适配器额外用到的）

| code | 说明 |
|---|---|
| `platform_conflict` | 这个 `platformId` 已经有别的适配器在线，或者公钥对不上 |
| `account_required` | 那个平台要求先绑定账号 |
| `link_failed` | 绑定没成 |
| `bad_handoff_url` | 适配器给的链接不在它声明的域名下（节点内部用，不发给玩家） |

## 实现时补全的细节（tablenet-node 0.1）

- **只收配置里登记过的平台。** `[adapters.<platformId>]` 没写的平台一律 `platform_not_allowed`。登记了但没钉公钥的，第一次上线的那把公钥记进 `data_dir/adapters.json`，之后换钥匙要 `tablenet-node admin adapter-key`。
- `venue.room.upsert` 的正文和 `room.open` 相同，另加：`localId`（必填，`[A-Za-z0-9_.-]{1,64}`）、`join`（`handoff`／`bridge`，默认握手时 `joinKinds` 的第一个）、`host.displayName`（可选，平台公开的展示名）、`extra`（只收 `x-` 开头的键，原样放进房间对象，例如 `x-hexproof-rules`）。带 `id` 时回 `venue.room.upserted {roomId}`。
- 桥接房必须带 `codec`，且是握手时 `platform.codecs` 里声明过的。
- 适配器回的 `error`（`re` 对上节点的请求编号）原样转给玩家；开房失败时双方回到排队，不算他们拒绝。
- `connect.server` 的主机名对照 `[adapters.<platformId>] servers` 检查；没登记任何服务器时，所有带 `server` 的 `connect` 都会被拦下。
