# 07 · 首批适配器：XMage 与 Hexproof（草案 0）

两个适配器都由我们自己写，放在本仓库 `adapters/` 下：XMage 适配器 MIT（XMage 本身是 MIT），Hexproof 适配器 GPL-3.0。
下面写清楚它们能做到哪一档、要连什么服务器，以及哪些地方还要实测确认（标 **待核**）。

## 总的判断

**两档都要做。交接档先通链路，桥接档才是独弈玩家真正要的。**
- 交接档：适配器把那个平台的房间搬进 Tablenet 的房间表，排队配到那个平台时替双方开房，告诉玩家「打开 XMage（或 Hexproof）客户端，连某某服务器，进某某房间」。玩家要装那个平台的客户端。
- 桥接档：玩家在独弈里直接打 XMage 或 Hexproof 服务器上的局，结算全交给对方。适配器把对方的局面和提问翻成独弈的 `arcane.v0`，独弈就像联机当客人一样打。设计见 [08](08-桥接模式.md)。

目标是：**一个 Tablenet 身份（公钥）、一张房间表、一个排队入口，背后可以落到独弈、XMage、Hexproof 三处之一，而且三处都能在独弈里打。**

## XMage

（2026-11-22 对照 `magefree/mage` master 源码核过，下文标 **待实测** 的是读代码得出、还没在真服务器上跑过的。）

### 要连什么

一台 XMage 服务器。可以是你自己部署的（推荐，compose 里带一份），也可以是别人运营的公共服务器（要先征得运营者同意，见 [02](02-适配器协议.md)）。

### 怎么写

- **许可证：XMage 是 MIT。** 所以 XMage 适配器也可以用 MIT，和节点本体一样。传输层依赖的 JBoss Remoting 是 LGPL，作为库调用不影响 MIT。
- **语言：** Java。客户端和服务器之间是 JBoss Remoting 的 `bisocket` 传输，传的是 Java 序列化对象（`GameView`、`TableView` 等），别的语言接不了。适配器直接依赖 XMage 的 `Mage.Common`，用它的 `SessionImpl`。
- **版本：** 登录接口 `connectUser(userName, password, sessionId, restoreSessionId, MageVersion version, userId)` 要带客户端版本，和服务器对不上就登不进去。适配器要跟服务器一起升级；启动时版本对不上，就以 `platform_conflict` 拒绝上线，并在日志里写明两边各是什么版本。
- **身份：** 交接档用一个机器人账号；桥接档每位独弈玩家各开一个会话（见 [08](08-桥接模式.md#账号与隐私)）。服务器开了注册的话，账号要先注册。

### 建桌和入座（读代码的结论）

用到的接口：`roomGetAllTables(roomId)`、`roomCreateTable(sessionId, roomId, MatchOptions)`、`roomJoinTable(sessionId, roomId, tableId, name, PlayerType, skill, DeckCardLists, password)`、`matchStart(sessionId, roomId, tableId)`、`tableRemove(...)`。

- **建桌的人不必自己坐下。** 建桌只登记桌主（`TableController.userId`），入座是另一个调用 `roomJoinTable`。
- **开打要桌主来按。** `startMatch(userId)` 只认桌主，而且要求所有座位都坐满（`allSeatsAreOccupied`）。所以适配器建了桌，要等两位玩家坐满，再替他们调 `matchStart`。
- **桌主在开打前离开，这张桌直接被删掉**（`leaveTable` 里桌子还在 `WAITING`／`READY_TO_START` 时会 `removeTable`）。所以适配器的机器人会话在开打前不能断；断了就要重新建桌、重发入座信息。**待实测**：开打之后桌主离开会不会影响对局。
- **入座要交牌组。** `roomJoinTable` 带 `DeckCardLists`，服务器当场验牌，不合法就拒绝入座（桌主交了不合法的牌组，桌子会被删）。交接档里玩家在 XMage 客户端里自己交，桥接档由适配器把独弈的牌组转过去。

### 能做的事

| Tablenet 动作 | XMage 那边 | 状态 |
|---|---|---|
| 发布房间 `venue.room.upsert` | 定时 `roomGetAllTables` 取主房间的桌子，把等人的桌子搬过来 | 可做 |
| 入座 `venue.seat.request` | 回 `connect`：服务器地址、端口、桌名、密码（如果有） | 可做；XMage 没有入座链接 |
| 按请求开房 `venue.room.create` | 机器人建一张带密码的桌（不坐下），把桌名和密码分别发给两位玩家，坐满后调 `matchStart` | 读代码可行，**待实测** |
| 结果回报 `venue.result` | 交接档：机器人不在桌上，收不到对局回调，只能轮询 `roomGetAllTables` 看桌子变成 `FINISHED`，胜负要从 `TableView` 里读 | **待实测**：`TableView` 里有没有胜负 |
| | 桥接档：适配器替玩家坐在桌上，直接收 `GAME_OVER`／`END_GAME_INFO` | 可做 |

### 赛制对照

XMage 的赛制叫法是 `Constructed - Standard`、`Constructed - Modern`、`Commander Free For All` 之类的字符串，写在 `MatchOptions` 的游戏类型和牌组类型里。适配器里放一张对照表，对不上的不发布。

## Hexproof

（2026-11-22 对照 `ClayStan404/hexproof` master 的 `protocol/v3` schema 和服务器源码核过，下文标 **待实测** 的是读代码得出、还没跑过的。）

### 要连什么

一个 Hexproof hub（`hexproof-server`，Go 写的，单文件，WebSocket 端点 `/ws`，健康检查 `/healthz`）。官方支持自建（`docs/self-hosting.md`），独立 hub 不要求账号，只用展示名和房号。
规则房要 hub 带 Forge 运行时：握手回的 `session.welcome.forgeRulesAvailable` 为真才开得了。

### 协议版本是个坑

- Hexproof 要求 `session.hello.protocol` 与 hub **完全相等**，没有协商、没有范围（`docs/protocol-compatibility.md`，作者 10-21 定的规矩）。
- **源码 master 已是 `hexproof.v3`，但它的官方 hub 10-25 才迁到 `hexproof.v2`。** 也就是说：自己用 master 源码编的 hub 讲 v3，官方 hub 讲 v2，同一个适配器连不了两边。
- 适配器按「目标 hub 讲哪个版本」分别构建，启动时读 `session.welcome.v`，和自己不一致就以 `platform_conflict` 拒绝上线。第一版只支持 v3（连自建 hub）。

### 怎么写

- **语言：** 随意，WebSocket＋JSON。初稿倾向 Go，可以直接对照 `protocol/v3` 的 schema 和 fixture 写。
- **许可证：** Hexproof 是 GPL-3.0，适配器照它的 schema 实现，同样用 GPL-3.0，避免争议。
- **握手：** `session.hello {displayName, clientVersion, protocol, resumeToken?}` → `session.welcome {v, connectionId, resumeToken, forgeRulesAvailable, …}`。断线续接用 `resumeToken`。

### 建房和入座（读 schema 的结论）

- 建房 `room.create`：名字、`format`（`modern`／`duel`／`edh`，这是牌桌类型，不是赛制）、`deckFormat`（赛制：standard、pioneer、modern、legacy、vintage、pauper、commander 等）、`maxSeats`、`matchMode`（`bo1`／`bo3`）、`rulesMode`（`manual` 手动／`forge` 规则）、`hostingMode`（`server`／`player`）、密码、观战开关。
- **建房的人自己就占一个座位**：`room.created` 回的是 `{roomId, settings, hostSeat}`。这一点和 XMage 不同。
- 入座 `room.join {roomId, asSpectator, password?}` → `room.joined {role, seat}`；之后 `deck.select` 交牌组（主牌、备牌、指挥官），`player.ready` 准备；开打前 hub 发 `match.load_required`，客户端要回 `client.load_complete`。
- `hostingMode: "player"` 是让某位玩家的电脑跑 Forge。适配器**必须**只开 `server`，不当玩家主机。

### 能做的事

| Tablenet 动作 | Hexproof 那边 | 状态 |
|---|---|---|
| 发布房间 | `room.list` → `room.listed`，每间带 `rulesMode`、`playerJoinable`、`hasPassword`、人数 | 可做 |
| 入座 | 回 `connect`：hub 地址加房号 | 可做；它没有入座链接 |
| 按请求开房（交接档） | 建房的人会占一个座位，所以适配器不能「替两个人建好再走开」。**待实测**：房主 `room.leave` 后房间是转让还是解散（协议里有 `room.disband`、`cannot_kick_host`，倾向于解散） | 有障碍。退路：配对后让其中一位在 Hexproof 客户端里建房，适配器只负责把房号转给另一位 |
| 按请求开房（桥接档） | 适配器替独弈玩家建房，那个座位本来就是这位玩家的 | 可做 |
| 结果回报 | 桥接档：在座位上，直接收 `game.snapshot.result`、`game.conceded`。交接档：适配器不在房里，**待实测**能否以观战者身份进去看结果 | 桥接可做 |

### 注意

- `rulesMode: "manual"` 的房间不裁决规则，玩家自己挪牌。发布房间时必须标出来（`x-hexproof-rules: "manual" | "forge"`），免得独弈玩家以为是自动裁决的局。
- 它自带官方集群和服务器目录（`docs/home-servers.md`、`docs/server-directory.md`），和 Tablenet 是两套东西。适配器只连一个 hub，不碰它的集群协调。

## 先后

1. **`adapters/example`** 和一致性测试工具：协议定下来先写它，节点和适配器两边都靠它验证。
2. **Hexproof 规则房桥接**（11-22 核过源码后提前）：WebSocket＋JSON、有 schema，提问一次交一整组，20 种 kind 都对得上独弈的十一种；桥接时建房者占座反而正合适。同时要动独弈前端，见 [08](08-桥接模式.md#独弈要做的事)。
3. **XMage 桥接档**（11-22 已做，见下文实现状态）：提问是一次点一个，适配器要拆组逐个回，还要靠消息文本分辨同一个回调的不同用途，比 Hexproof 难；另外要处理 Java 依赖和跟服务器版本升级。
4. **两家的交接档**：XMage 交接档读代码可行（建桌不占座）；Hexproof 交接档卡在「建房者占座」，先实测房主离开的行为再定做法。
5. **独弈手动桌模式**，接 Hexproof 手动房。

桥接不依赖「替别人建房」，所以交接档的待实测项不挡桥接。

## 实现状态（11-22）

`adapters/hexproof` 0.1 已写：大厅镜像、交接、规则房桥接、排队建房（由第一位能桥接的玩家的会话建，避开「建房者占座」）。20 种 `kind` 全有对照，`scry` 退化成逐张选去处。用照 schema 写的模拟 hub＋真节点测过，发出的 123 帧全部通过 `arcane.v0` schema。11-22 已连本机自建的 Hexproof 3.4.0 实测：座位号、错密码码、认输回话、房主离开即解散都已确认；查出两处要改并已改——牌组每张都要带系列和收藏编号（适配器先拦）、`client.load_complete` 必须带 id。同日装上 Forge 运行时后，规则房桥接在真 hub 上打完了一整局（1671 帧全过 schema），又查出并修了五处：开局时大厅撤房把桥接通道连带关掉（节点和适配器两边都改）、座位坐满才能准备、开局失败要转告玩家、回答被拒要重问、付不起时不发对方没提供的选项。宣告阻挡等几种提问还没在真 hub 上遇到。没做 BO3 换备、重连、观战。详见该目录的 README。

`adapters/xmage` 已写（11-22，0.2）：**接的是别人已经在运营的 XMage 服务器**（一个适配器可接多台，每台一个大厅机器人账号），不自带服务器；允许不注册登录的服务器做桥接，要注册的只做交接。Go 主体讲 Tablenet、翻译 `arcane.v0`，Java 驱动用 XMage 的 `SessionImpl` 连服务器（一个进程多个会话），两段之间走标准输入输出 JSON Lines。大厅镜像、交接、桥接、排队开桌都有。连本机 XMage 1.4.63-V2 实测：桥接整局打完、排队开桌（一位桥接、一位拿交接信息去 XMage 坐）打完，1251 帧全过 `arcane.v0` schema。上面标「待实测」的几处，实测结果：
- **建桌的人不必坐下**：属实。机器人建桌不坐，两位玩家坐满后桌子变 `READY_TO_START`，机器人调 `matchStart` 开打。
- **`TableView` 里没有胜负**：交接档拿不到结果，只有桥接玩家的局能报 `venue.result`（从 `END_GAME_INFO` 读）。而且 `GameEndView.getLoses()` 输家也是 0，盘打没打完要看 `matchInfo` 文字。
- 另外查出：用 Java 17 跑的 XMage 服务器和客户端都要加 `--add-opens java.base/java.io` 等，不然一连就断；`Constants.Option` 的键是 `possibleAttackers` 这样的驼峰名，不是常量名；「哪个触发先上堆叠」的候选在 `cards1` 里、`targets` 是空的。
没做：BO3 换备（原样交回同一副牌）、观战、断线重连。详见该目录的 README。
